# 営業支援AIチーム アーキテクチャ（フェーズ1：防災・予算/議事録分析）

個人の営業活動を支援するため、WEB上の公開情報を整理する専門エージェントチーム。
フェーズ1は **防災領域** に特化し、**予算資料** と **議会議事録** の収集・分析に絞る。
対象自治体は固定せず、実行時に指定する **汎用設計**。

## 設計の基本思想

精度を高めるため、**収集(Collect)・分析(Analyze)・検証(QA)を明確に分離**する。

- 収集役: 事実を漏れなく、出典付きで集めるだけ。解釈・推測をしない。
- 分析役: 渡された一次情報のみで考える。自分で再検索しない。
- 検証役: 出典のない主張・事実と推測の混同を棄却し、成果物に統合する。

この分離により、「拾い漏れ（収集の問題）」と「読み違い（分析の問題）」を
別々のチェックポイントで潰せる。

## チーム構成（6エージェント）

| # | エージェント | 層 | 役割 | 主な入出力 |
|---|---|---|---|---|
| 1 | director | 統括 | 調査計画(リサーチプラン)の設計 | 入力:自治体名/目的 → 出力:計画書 |
| 2 | collector-budget | 収集 | 防災予算の出典付き収集 | → budget_raw.md |
| 3 | collector-minutes | 収集 | 防災関連発言の出典付き収集 | → minutes_raw.md |
| 4 | analyst-budget | 分析 | 予算から案件化の兆候を読む | budget_raw.md → budget_analysis.md |
| 5 | analyst-needs | 分析 | 議事録から課題/切り口/キーパーソン抽出 | minutes_raw.md → needs_analysis.md |
| 6 | qa-editor | 品質 | 検証して営業向けレポートに統合 | 全成果物 → report.md |

## オーケストレーション（重要な実装上の制約）

Claude Code のサブエージェントは **自分から別のサブエージェントを呼び出せない**。
そのため指揮は **メインセッション** が行う:

```
1. メインセッションが director を呼ぶ → リサーチプランを得る
2. メインセッションがプランに従って順に呼ぶ:
     collector-budget → collector-minutes
        → analyst-budget → analyst-needs
        → qa-editor
3. 各エージェントは workspace/<自治体>/ にファイルで成果物を残し、
   次のエージェントはそれを読んで作業する（ファイル受け渡し）
```

director は「指揮官」ではなく「作戦立案者」。実行はメインセッションが担う。

## 全エージェント共通の品質ルール

- **事実 / 出典URL / 日付 / 推測** を必ず区別して記述する。
- 出典のない主張は QA で棄却し「要確認事項」へ隔離する。
- 自治体名・URL・金額・発言を **創作しない**。取得不可なら正直に明記する。
- 推測には **確度（高/中/低）** を付す。

## 使い方（例）

メインセッションに対して、例えば次のように依頼する:

> 「○○市の防災について調査して。まず director で計画を立てて、その計画どおりに
>  各エージェントを順に動かし、最後に report.md を作って。」

## ロードマップ

- **フェーズ1（本書）**: 防災 × 予算/議事録分析。
- **フェーズ2**: 入札公告クローラー / 入札過去実績リサーチャー＋入札傾向アナリストを追加。
- **フェーズ3**: 競合分析・コンサル比較アナリストを追加。対象分野を防災以外へ拡張。

いずれも同じ「収集／分析／QA分離」の枠組みにエージェントを足す形で拡張する。

## 注意：ネットワーク到達性

収集エージェントは WebSearch / WebFetch を使う。実行環境のネットワークポリシーに
よっては自治体サイトやPDFへ到達できない場合があるため、本格運用前に到達性を確認する。
JS描画サイトやPDFが多い場合は、専用のクローラー/PDF抽出MCPサーバーの追加を検討する。
